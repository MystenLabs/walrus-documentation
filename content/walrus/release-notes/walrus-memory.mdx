### Walrus Memory MCP v0.0.18

October 30, 2026 | [GitHub](https://github.com/MystenLabs/walrus-memory/releases/tag/%40mysten-incubation/memwal-mcp%400.0.18)

#### Changes

- [`MEMWAL_AUTO_SAVE` in `process.env` can no longer turn automatic memory on or clear `pendingConsent`. An MCP client populates `env` from `.cursor/mcp.json`, `.vscode/mcp.json`, or `.claude/settings.json` inside the checkout, so a truthy `MEMWAL_AUTO_SAVE` in `env` could flip automatic saving on over a stored `autoSave: false` (reporting `enabled: true` alongside `state: "off"`) or bypass the consent prompt on an unanswered install. Both the MCP server and the plugin hooks now honour only a disabling override (`MEMWAL_AUTO_SAVE=0`) from `env`, keep `state` and `enabled` consistent, and preserve `pendingConsent: true` until a stored answer exists in `~/.memwal/settings.json`.](https://github.com/MystenLabs/MemWal/pull/995)

### Walrus Memory MCP v0.0.17

October 28, 2026 | [GitHub](https://github.com/MystenLabs/walrus-memory/releases/tag/%40mysten-incubation/memwal-mcp%400.0.17)

Unreleased. Package and plugin manifests are bumped manually to 0.0.17. The launcher installs the published 0.0.16 through `mcpPackageVersion` until 0.0.17 is available on npm; retarget that pin after publishing.

#### Changes

- [`memwal_remember_bulk` no longer registers a second paid Walrus blob when the bridge reconnects and replays the call. The bridge stamps each call with a stable idempotency key before tracking it, and the sidecar sends that key to the relayer, which answers a replayed key with the jobs it already queued. A bulk call the agent retries itself is a new call and gets a new key.](https://github.com/MystenLabs/MemWal/pull/1045)

### Walrus Memory MCP v0.0.16

October 26, 2026 | [GitHub](https://github.com/MystenLabs/walrus-memory/releases/tag/%40mysten-incubation/memwal-mcp%400.0.16)

This release updates `@modelcontextprotocol/sdk` to 1.32.1, which includes transport security fixes.

Authenticated SSE GET and POST requests now refuse redirects. The message endpoint that the server
supplies must stay on the configured relayer origin. Because of this, custom authentication headers
and tool arguments cannot be forwarded to a redirected origin. If your deployment relies on
redirects to reach the relayer, configure the final relayer URL directly.

### Walrus Memory MCP v0.0.15

October 21, 2026 | [GitHub](https://github.com/MystenLabs/walrus-memory/releases/tag/%40mysten-incubation/memwal-mcp%400.0.15)

A project-local `.memwal/credentials.json` is ignored until you approve that exact project path,
account, delegate key, and relayer with `memwal-mcp approve-project`. Approvals are stored in
`~/.memwal/project-approvals.json`, and any change to the destination requires approving again.
Until then, the global credentials are used and a stderr line names the skipped file.
`memwal_health` now reports `account=` beside `relayer=`.

`MEMWAL_CREDS_DIR` must now be an absolute path outside the current project. Other values are
refused with an error, and an empty value means unset. The login write-ahead record moves out of the
repository to `~/.memwal/login-pending/`. `memwal_login` with `freshKey: true` now closes the
previous listener and names the abandoned public key and address so you can remove them from the
dashboard.

### Walrus Memory MCP v0.0.14

September 22, 2026 | [GitHub](https://github.com/MystenLabs/walrus-memory/releases/tag/%40mysten-incubation/memwal-mcp%400.0.14)

The plugin no longer starts the MCP server through `npx`, which could run a package planted in the
open project. Every launch site now runs `plugin/scripts/launch_mcp.mjs`. It installs the pinned
version under `~/.memwal/runtime` and fails rather than falling back. `MEMWAL_MCP_RUNTIME_DIR`
relocates that directory and must be an absolute path.

`memwal_remember` and `memwal_remember_bulk` now return a `job_id` at accept by default. Set
`MEMWAL_MCP_REMEMBER_WAIT_MS=90000` to wait for a `blob_id`. Set `MEMWAL_MCP_TRANSPORT=http` to use
Streamable HTTP, though replayed writes might duplicate. Timeouts report the cause and relayer
health. The bridge honors `retry_after`, `memwal_remember_status` accepts `job_ids`, and delegate
keypairs persist before browser sign-in.

#### Changes

- [The cold-start tool list no longer advertises a tool the relayer may not serve. The bridge ships on npm and updates itself while a relayer ships per environment, so 0.0.14-dev.0 dialled prod and staging still on 0.0.13: cold start named `memwal_remember_status`, which neither registers, and the pending-write wording sent the agent to go call it — one live run spent 90.67s there before erroring. Cold start is now a floor rather than a forecast (`BASELINE_RELAYER_TOOLS`): it carries only what the oldest supported relayer serves and its descriptions name nothing outside it, while newer tools still reach the client a beat later on the relayer's own `tools/list`. Initialize `instructions` use the same floor (they used to name `memwal_remember_status` before any `tools/list`). And a call for a tool outside that floor — including during the cold-start window, before any upstream `tools/list` has been seen — is now answered locally and at once — naming the tools that do exist and saying plainly that nothing ran — instead of being forwarded into a wait that only ends at the orphan deadline.](https://github.com/MystenLabs/MemWal/pull/928)

### Walrus Memory MCP v0.0.13

September 15, 2026 | [GitHub](https://github.com/MystenLabs/walrus-memory/releases/tag/%40mysten-incubation/memwal-mcp%400.0.13)

Timed-out writes from `memwal_remember`, `memwal_remember_bulk`, and `memwal_analyze` now warn that
the write might have completed and tell you to check with `memwal_recall` before re-saving, which
avoids duplicate paid copies. The bridge reports a rejected delegate key immediately and points to
`memwal_login`. It backs off on HTTP 429 using `Retry-After`. It fails requests stuck behind a
failing handshake after 90s, which you can override with `MEMWAL_MCP_STALLED_HANDSHAKE_MS`.

After an in-session `memwal_login`, the bridge keeps reading stdin and confirms the sign-in. The CLI
writes credentials as a new `0600` file, warns about unrecognized options, and lists network presets
in `--help`. `memwal_health` now reports the relayer URL, and `memwal_restore` retries a page after
a transient failure.

#### Changes

- [Unrecognised options now warn on stderr and in the structured log (`cli.unrecognised_arg`) instead of being dropped in silence, so a typo'd `--namesapce work` no longer writes to the default namespace with nothing to say it had. The warning names the option key only, keeping a mistyped value-taking flag (`--tokenn=hunter2`) from putting the secret on stderr, and it warns rather than exits so an option from a newer config cannot brick the server.](https://github.com/MystenLabs/MemWal/pull/630)
- [`--help` now lists the network presets (`--prod`, `--dev`, `--staging`, `--local`) with the relayer and web URLs each resolves to, rendered from the preset table rather than retyped so a new preset cannot ship undocumented the way `--prod` did. The `--label` default is corrected to "MCP Client", which is what the code actually falls back to.](https://github.com/MystenLabs/MemWal/pull/630)
- [`memwal_health` reports `relayer=<url>`, naming the origin this process dialled, so a client bound to the wrong network finds out there instead of by noticing its memories are missing. The URL is captured when the call is sent rather than when the reply lands, so a reconnect mid-flight cannot label the answer with a relayer it did not come from.](https://github.com/MystenLabs/MemWal/pull/630)
- [Keep reading stdin after an in-session `memwal_login`. The auth-required stub hands off to the bridge by pausing stdin, and a stream paused that way does not resume when a new `data` listener attaches, so the bridge served only the request replayed from the hand-off and then went deaf. Signing in appeared to work, the retry succeeded, and every call after it hung until the client timed it out.](https://github.com/MystenLabs/MemWal/pull/633)
- [Confirm a completed sign-in instead of only writing it to the log file. The failure path already reported itself twice (a notification and a notice on the next tool call) while success reported nothing, so a user who approved in the browser could not tell whether credentials had landed, the bridge had adopted them, or a retry was worth trying. Success now sends the matching notification and prefixes a one-shot banner naming the account, the delegate, and the resolved credentials path onto the next tool result.](https://github.com/MystenLabs/MemWal/pull/633)
- [Stop the `memwal_login` prompt claiming you are already signed in when you are not. The bridge assumed it only ever runs with credentials on disk, but `memwal_logout` deletes them and login is intercepted before the signed-out guard, so a login after a logout in the same session announced that a stored delegate key would be replaced, reading as though the logout had not taken. Both prompts now read the credentials file instead of assuming the mode.](https://github.com/MystenLabs/MemWal/pull/633)
- [Write the credentials file by creating a new `0600` file and renaming it into place, instead of writing the delegate private key to the existing path and tightening the permission afterwards. `writeFileSync`'s `mode` only applies when it creates the file, so a `credentials.json` left world-readable by anything outside the CLI (a manual `chmod`, a restored backup, another tool) received the new key under the old permission until the following `chmod` landed. The CLI now writes the backup it takes when signing in as a different account the same way; that backup holds the same plaintext key, and the CLI previously created it under the process umask. On Windows, where `rename` cannot replace a destination another process holds open and POSIX mode bits are not enforced at all, the CLI retries briefly and then writes in place rather than failing the sign-in.](https://github.com/MystenLabs/MemWal/pull/520)

### Walrus Memory MCP v0.0.12

September 9, 2026 | [GitHub](https://github.com/MystenLabs/walrus-memory/releases/tag/%40mysten-incubation/memwal-mcp%400.0.12)

`memwal_recall` accepts an optional `maxDistance` cosine-distance cutoff, which must be 0 or
greater. It drops hits with `distance >= maxDistance`, and result lines now show both `score` and
`distance`. The server forwards the client's `initialize.clientInfo` to the relayer as
`x-memwal-client` and `x-memwal-client-version`, so sidecar logs name the coding agent.

The credential directory now resolves on every access, and `MEMWAL_CREDS_DIR` overrides it. This
fixes a Windows problem where the test suite overwrote `~/.memwal/credentials.json` and its delegate
key. `memwal_restore` now clarifies that `truncated=true` is retryable and that `truncated=false`
does not guarantee completeness.

#### Changes

- [Optional `maxDistance` on `memwal_recall`: cosine-distance cutoff (low = similar, must be >= 0). Hits with `distance >= maxDistance` are dropped. Result lines now include both `score` (`1 − cosine distance`) and `distance`.](https://github.com/MystenLabs/MemWal/pull/373)
- [Resolve the credential directory on every access instead of freezing it at module load, and let `MEMWAL_CREDS_DIR` override it. The login test sandboxed the home directory with `HOME` alone, which `os.homedir()` ignores on Windows, so running the package's test suite there wrote fixture credentials over the developer's real `~/.memwal/credentials.json` and destroyed the delegate key stored in it.](https://github.com/MystenLabs/MemWal/pull/705)

### Walrus Memory MCP v0.0.11

August 24, 2026 | [GitHub](https://github.com/MystenLabs/walrus-memory/releases/tag/%40mysten-incubation/memwal-mcp%400.0.11)

This release fixes MCP bridge reliability. The SSE handshake socket no longer aborts on HTTP 429,
401, or a bad content-type, which crashed on Windows. Outbound MCP POSTs are serialized, and the
bridge reconnects when the SSE handle is gone. A burst of `memwal_recall` calls no longer breaks it
until restart.

`login` without a TTY exits with code 1 instead of reporting success. Concurrent `memwal_login`
calls reuse the in-flight listener and URL rather than starting a second flow that can hang later
remember and recall calls. A login timeout warns that an on-chain delegate key might already exist
if the browser approved after the listener expired. Session occupancy caps are reported as
concurrent limits rather than a 30-second cooldown.

### Walrus Memory MCP v0.0.10

August 20, 2026 | [GitHub](https://github.com/MystenLabs/walrus-memory/releases/tag/%40mysten-incubation/memwal-mcp%400.0.10)

The MCP server now sends proactive-usage instructions in the MCP `initialize` handshake. The model
knows when to save and recall memories even when your client lazily loads tool descriptions. The
bridge carries these instructions at cold start. Signed-out sessions get guidance pointing at
`memwal_login` and a conservative `tools/list`. `memwal_recall` is advertised as read-only. The
UserPromptSubmit hook lets the agent choose between remember and recall from meaning rather than
keywords.

Tool calls whose upstream response never arrives return a retryable error after
`MEMWAL_MCP_CALL_TIMEOUT_MS` (default 240s) instead of hanging. `memwal_remember_bulk` uses your
configured namespace (`--namespace` / `MEMWAL_NAMESPACE`) when a call omits one.
`serverInfo.version` reports the real package version.

#### Changes

- [Answer orphaned tool calls whose upstream response never arrives with a retryable error instead of hanging indefinitely. The bridge now tracks in-flight request start times and sweeps expired calls through a per-request deadline (`MEMWAL_MCP_CALL_TIMEOUT_MS`, default 240s), reuses the existing late-reply drop so an expired call cannot get a second response, and enriches reconnect logs with pending request IDs and methods.](https://github.com/MystenLabs/MemWal/pull/690)
- [Inject the configured default namespace (`--namespace` / `MEMWAL_NAMESPACE`) into `memwal_remember_bulk` calls that omit one, so bulk facts land in the project namespace instead of the relayer fallback `default`.](https://github.com/MystenLabs/MemWal/pull/667)
- [Send proactive-usage instructions in the MCP `initialize` handshake, so the model knows when to save and recall without being asked. Clients moved to lazy tool loading, which keeps tool descriptions out of the model's context until a tool is explicitly loaded; the guidance lived only in those descriptions, so the model stopped using memory on its own and would offer its built-in memory or deny the tool existed. `instructions` travels with `initialize`, before any `tools/list`, so lazy loading cannot strip it.](https://github.com/MystenLabs/MemWal/pull/681)

### Walrus Memory TypeScript SDK v0.1.11

October 28, 2026 | [GitHub](https://github.com/MystenLabs/walrus-memory/releases/tag/%40mysten-incubation/memwal%400.1.11)

#### Changes

- [`remember`, `rememberAsync`, and `rememberAndWait` accept `{ dedupe: true }` (`RememberOptions` / `RememberWaitOptions`) for opt-in content-hash deduplication per `(owner, namespace, text)` without a 30-minute time window. When `dedupe: true` is set, the client derives a bucket-less `dedupe:<sha256>` key and sends `dedupe: true` to `POST /api/remember`, collapsing duplicate writes onto the existing live job and `blob_id` while writing fresh if the memory was later forgotten or deleted. `MemWalMock` mirrors the same behavior.](https://github.com/MystenLabs/MemWal/pull/769)
- [`formatUntrustedMemories` and `withMemWal` validate that each recalled memory's `distance` is a finite number and clamp similarity relevance (`1 - distance`) to `[0, 1]` before filtering and formatting. Records with `undefined`, `NaN`, or `±Infinity` distances are dropped instead of rendering `"relevance":"NaN"`, and negative or greater-than-one distances are clamped to `1.00` / `0.00`.](https://github.com/MystenLabs/MemWal/pull/976)
- [`MemWal.listNamespaces` and `MemWal.listMemories` reject a `limit` that is not a positive integer before signing the query string, with the same `limit must be a positive integer, got <limit>` `TypeError` as `recall` and `recallManual`.](https://github.com/MystenLabs/MemWal/pull/1213)
- [`analyze()` accepts an optional `signal` in `AnalyzeOptions` and aborts the in-flight `/api/analyze` HTTP request when the caller's `AbortSignal` fires.](https://github.com/MystenLabs/MemWal/pull/1095)
- [`MemWal.rememberManual`, `MemWal.recallManual`, `MemWalManual.rememberManual`, and `MemWalManual.recallManual` reject an empty or non-finite `vector` (including `NaN`, `±Infinity`, non-number elements, and sparse arrays) before signing, and `rememberManual` rejects a missing or blank `encryptedData` string with `TypeError`.](https://github.com/MystenLabs/MemWal/pull/1211)

### Walrus Memory TypeScript SDK v0.1.10

October 26, 2026 | [GitHub](https://github.com/MystenLabs/walrus-memory/releases/tag/%40mysten-incubation/memwal%400.1.10)

This release tightens input and response validation in the Walrus Memory SDK. `recallManual` on
`MemWal` and `MemWalManual` rejects `NaN` or `Infinity` in `scoringWeights` before signing, matching
`recall`. Previously, `JSON.stringify` sent these values to the relayer as `null`. `remember`,
`rememberBulk`, `analyze`, `embed`, and `recall` also reject text containing only whitespace and
zero-width characters. Previously, these calls waited until the client timed out. `MemWalMock`
rejects the same input.

When a 2xx response has the wrong JSON shape, the SDK raises an error naming the endpoint and the
missing array instead of a raw `TypeError`. The SDK does not retry these bulk status errors. A null
or non-object status body makes `getRememberStatus` return `not_found` and `waitForRememberJob`
throw `MemWalRememberJobNotFoundError`.

### Walrus Memory TypeScript SDK v0.1.9

October 21, 2026 | [GitHub](https://github.com/MystenLabs/walrus-memory/releases/tag/%40mysten-incubation/memwal%400.1.9)

`createAccount`, `addDelegateKey`, `removeDelegateKey`, and `MemWalManual` work again without a
`suiClient`. The default is now `SuiGrpcClient` against the public fullnode for `suiNetwork`.
`rememberBulk` and `rememberBulkAsync` send a derived idempotency key, so a retry within 30 minutes
returns the same jobs. `listMemories()` pages stored memories as metadata without a similarity
query.

Remember-job waits back off toward a 5s cap. On timeout they raise `MemWalRememberJobTimeout` with
`lastStatus` and `serverError`, and they raise `MemWalRateLimited` when status reads stay
rate-limited. Many methods reject invalid input before signing, including bad `limit`,
`maxDistance`, job ids, and blank text. Package subpaths now resolve in Next.js, Turbopack, and Node
`require(esm)`, and `/manual` no longer imports `@mysten/walrus`.

#### Changes

- [`rememberBulk` and `rememberBulkAsync` send an idempotency key derived from the batch (a 30-minute bucket plus each item's namespace and text). A retry inside that window returns the same jobs instead of storing the batch again. An explicit `idempotencyKey` still wins.](https://github.com/MystenLabs/MemWal/pull/1080)
- [`withMemWal` does not recall or auto-save on a tool-execution step. A later tool step reuses the recall cached for that user message. Auto-save still runs only on a user turn.](https://github.com/MystenLabs/MemWal/pull/1079)
- [`flush()` raises when a background auto-save failed, and `onSaveError` runs. The chat turn itself still does not fail.](https://github.com/MystenLabs/MemWal/pull/1117)
- [`waitForRememberJob` and `waitForRememberJobs` do not sleep past the deadline. If the budget runs out during the sleep, they make one more status read.](https://github.com/MystenLabs/MemWal/pull/1081)
- [`remember`, `rememberAsync`, and `rememberAndWait` reject a non-string text argument with `TypeError` before signing. An object used to be sent as `text` and the relayer answered 422.](https://github.com/MystenLabs/MemWal/pull/1058)
- [`MemWalMock.rememberBulkAsync` rejects an empty or non-array batch with the same error as `MemWal`.](https://github.com/MystenLabs/MemWal/pull/1146)
- [`MemWalMock` honors `idempotencyKey`. A retry of the same text and namespace returns the original job, a different payload throws, and `forget` / `clear` release the key so the text can be written again.](https://github.com/MystenLabs/MemWal/pull/1147)
- [`MemWalMock.recall({ sort: "recent" })` orders a bounded semantic window (5× `limit`, at least `limit`, at most 50) by write time before truncating. Relevance order is unchanged.](https://github.com/MystenLabs/MemWal/pull/1124)
- [Positional `recall(query, options, namespace)` uses that namespace when `options.namespace` is omitted, on both `MemWal` and `MemWalMock`. An explicit `options.namespace` still wins.](https://github.com/MystenLabs/MemWal/pull/1038)
- [`remember(text, { idempotencyKey })` and `rememberAndWait(text, { timeoutMs }, { idempotencyKey })` treat a plain object in the namespace slot as options. A third options argument is merged, and its fields win. That call used to send the object as the namespace, or drop the third argument and mint a second blob. An explicit string namespace still wins.](https://github.com/MystenLabs/MemWal/pull/1142)
- [`getRememberStatus("")` returns `not_found` without a request, and `waitForRememberJob("")` fails immediately with status 404. `GET /api/remember/` is not a route; the empty 404 body used to throw `SyntaxError`, and the wait treated that as transient until timeout.](https://github.com/MystenLabs/MemWal/pull/1087)
- [`rememberBulkAsync` rejects more than 20 items before signing, matching the relayer's `MAX_BULK_ITEMS`.](https://github.com/MystenLabs/MemWal/pull/1104)
- [Remember-job status reads (`getRememberStatus`, `waitForRememberJob`, `getRememberBulkStatus`) no longer attach `x-seal-session`. Status is metadata and does not decrypt.](https://github.com/MystenLabs/MemWal/pull/1135)
- [Bulk status includes each job's `namespace`. `waitForRememberJobs(jobIds)` uses that value when the caller did not pass one, instead of the client default. A caller-supplied namespace still wins.](https://github.com/MystenLabs/MemWal/pull/1136)
- [`getPublicKeyHex()` and any request after `destroy()` throw, including a read already in flight. `getPublicKeyHex()` used to resolve to the zeroed key, or to the well-known key of the wiped seed, and `remember()` still sent `GET /version` before noticing the client was destroyed.](https://github.com/MystenLabs/MemWal/pull/1090)
- [`normalizeServerUrl` no longer warns about plaintext HTTP for IPv6 loopback. `URL.hostname` keeps the brackets on `[::1]`, so the `::1` exemption never matched `http://[::1]:8000`.](https://github.com/MystenLabs/MemWal/pull/1128)
- [`remember`, `rememberBulk`, `analyze`, and `embed` reject whitespace-only text immediately, with the same messages the relayer returns. A blank body used to be accepted and then sit until the client timed out.](https://github.com/MystenLabs/MemWal/pull/1129)
- [A 401 `AUTH_REJECTED` now says a wallet address is not a MemWal account ID. The relayer still returns one 401 for every credential failure, so the message names the mix-up instead of revealing which check failed.](https://github.com/MystenLabs/MemWal/pull/1132)

### Walrus Memory TypeScript SDK v0.1.8

September 22, 2026 | [GitHub](https://github.com/MystenLabs/walrus-memory/releases/tag/%40mysten-incubation/memwal%400.1.8)

All relayer requests now carry a deadline, so one stalled request no longer runs past `timeoutMs`.
Requests default to 30 seconds, and you can change this with `requestTimeoutMs` on `MemWal.create`.
`restore` and `analyze` each use 60 seconds. An expired request raises `MemWalRequestTimeout` with
`status: 504`, which the existing poll handling retries.

Generated idempotency keys now derive from the namespace, the text, and a 30-minute bucket. A replay
from a new client therefore no longer creates a duplicate paid Walrus blob. Explicit
`idempotencyKey` values are unaffected. `recall()` also sends `deadline_ms`. Relayers that read it
return a 504 with `serverCode` `RECALL_TIMEOUT` that names the stuck step.
